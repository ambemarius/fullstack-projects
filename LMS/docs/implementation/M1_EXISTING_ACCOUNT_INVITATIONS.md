# Existing-account administrator membership invitations

27 October 2026. **Subsequently mounted at the owner's explicit request, with verified local-profile enforcement and LYCEE_BATOURI restriction.** See M1_INVITATION_MOUNT.md for the current deployed behavior and 78 isolated/15 SQL test evidence. The staged notes below describe the earlier broader engine. Cross-school/new-profile provisioning remains gated; no real invitation or privilege was issued by activation. M1 remains in progress.

## Purpose and authority

This flow is separate from pending-school bootstrap and from new-account/password provisioning. An authenticated **platform_operator** can issue a fixed school-admin invitation for an explicitly selected active existing account and an already-active school. Ordinary school administration and school_onboarding alone cannot issue it. Student identities are excluded from administrator invitations. No caller can choose a different role, issuer, credential, expiry or inferred identity.

The intended recipient must authenticate as that same existing account before accepting the high-entropy invitation token. Possession of the token alone, a matching email, another account's session or the stored token hash is insufficient. An active existing target-school membership can explicitly gain admin without deleting its other roles; a revoked/pending membership requires separate recovery and is never silently reactivated. No account/credential is created, reset or merged. Acceptance does not automatically switch the recipient's active school or confer platform authority.

## Implementation

- model/identity/membershipInvitationService.js: issue/accept/list/revoke. Reuses school_invitations without a migration; stores only SHA-256 token hash, fixed admin role, 24-hour expiry and a reserved existing-admin binding containing exact account ID plus a digest of its current canonical login key. Canonical-key change invalidates the binding. Raw invitation token is returned only on issuance; list/revoke use the non-bearer hash identifier.
- SQL transactions revalidate actual account-session security version/expiry/revocation, active membership or platform-session authority, issuer account/grant and target-school state. Per-school/account application locks serialize grants. An invitation-row lock enforces single consumption. Audit is in the same transaction; failure rolls back the membership, role and consumption together.
- Issue rejects an already-active duplicate invitation and existing admin role. Acceptance rejects replay, expiry, revocation, disabled accounts, revoked issuer permission, wrong recipient, source pupil identity and changed/revoked membership. Old roles and passwords remain unchanged.
- routes/identity/membershipInvitationRouter.js is a factory only. It supports POST existing-admin, POST accept-existing-admin, GET existing-admin?schoolId=..., and POST existing-admin/:id/revoke under a future mount. It requires authentication, exact HTTPS Origin and CSRF on mutations, rejects identity/role injection and bounds attempt tracking. It sends no email/message and provides no automatic delivery.
- Pending-school inviteSchool/acceptInvitation now reserve/reject the existing-admin: namespace to prevent the overloaded legacy column from confusing these two purposes. Original migrations/checksums were not edited. This code is source-tested; live listeners were not restarted for this unmounted increment.

A membership alone does **not** provision a second local staff/admin profile, and legacy_account_map still has one-account uniqueness.
